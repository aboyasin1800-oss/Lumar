# LUMAR ERP OFFICIAL DATABASE POLICY

## Mandatory status

This policy is MANDATORY 100% for all database ownership, validation, write protection, and validation baseline decisions in LUMAR ERP. No other database policy or operational shortcut may override it without an explicit decision from the owner.

## Source of truth

This is the single authoritative policy for database ownership, validation, and write protection in LUMAR ERP. All other database-related references must point back to this policy rather than restating its decision in parallel.

## 10) حماية المنطق العامل ومنع Regression

تُعد هذه القاعدة جزءًا لا يتجزأ من السياسة الرسمية للمشروع، وتطبق على جميع المهام في Backend وFlutter وقواعد البيانات والخدمات والواجهات والعمليات المالية وأي جزء آخر من النظام.

### المبدأ الأساسي

القاعدة الأساسية هي:

```text
المنطق السليم العامل لا يُمس بلا ضرورة مثبتة.
```

ولا يجوز:

- إصلاح وظيفة بكسر وظيفة سليمة أخرى.
- اعتبار نجاح الميزة الجديدة دليلاً على صحة التنفيذ إذا أدى التنفيذ إلى Regression في السلوك السابق.
- الاعتقاد أن التغيير الجديد ناجح فقط لأن الوظيفة الجديدة تعمل، إذا تم كسر السلوك القائم الصحيح.

النجاح الحقيقي يعني:

- أن السلوك القديم الصحيح ما زال يعمل.
- أن السلوك الجديد المطلوب يعمل.
- عدم وجود Regression مثبت ناتج عن التعديل.

### قبل لمس منطق قائم

قبل تعديل أي منطق قائم يعتقد المنفذ أنه سليم أو تعتمد عليه وظائف قائمة، يجب أولاً تحديد السلوك الحالي وإثباته.

إذا كان هناك اختبار مناسب قائم، يجب تشغيله قبل التعديل.

إذا لم يوجد اختبار مناسب وكان السلوك قابلاً للاختبار بصورة آمنة، يجب إنشاء أو استخدام أقل اختبار Regression مناسب يثبت السلوك المراد حمايته قبل تغيير منطقه، دون إعادة تصميم المنطقة لمجرد إنشاء الاختبار.

يجب تسجيل:

1. ما المنطق الحالي؟
2. ما السلوك الصحيح الذي يؤديه؟
3. ما الاختبار أو الدليل الذي يثبته؟
4. هل الاختبار ناجح قبل التعديل؟
5. لماذا تحتاج المهمة الحالية إلى لمس هذا المنطق؟

إذا أثبت الاختبار أن المنطق الحالي سليم، فالأصل:

```text
DO NOT MODIFY IT.
```

### استثناء: عندما يجوز تعديل المنطق السليم

يجوز تعديل منطق سليم فقط عندما يثبت المنفذ التقني أن المهمة الجديدة لا يمكن تنفيذها بشكل صحيح وآمن ومستدام من دون تعديل ذلك المنطق.

عندها يجب قبل التعديل تحديد:

- لماذا التعديل ضروري؟
- لماذا لا يكفي التوسيع أو الإضافة من الخارج؟
- ما السلوك السابق الذي يجب المحافظة عليه؟
- ما السلوك الجديد المطلوب؟
- ما المخاطر؟
- كيف سيتم منع Regression؟

ويجب اختيار أقل تعديل آمن يحافظ على العقود والسلوك القائم.

### شرط عدم حدوث Regression

إذا أصبح تعديل المنطق السليم ضرورياً، فحفظ الوظيفة القديمة شرط قبول إلزامي، وليس توصية.

أي:

```text
OLD VALID BEHAVIOR + NEW REQUIRED BEHAVIOR = ACCEPTABLE CHANGE
```

أما:

```text
NEW REQUIRED BEHAVIOR + BROKEN OLD BEHAVIOR = FAILED IMPLEMENTATION
```

حتى لو أصبحت المهمة الجديدة تعمل.

### اختبار قبل / اختبار بعد

عند تعديل منطق سليم أو منطق مشترك:

- قبل التعديل: شغّل الاختبار أو الإثبات المناسب، وسجّل Baseline، وأثبت أن السلوك القديم يعمل.
- بعد التعديل: أعد نفس اختبار السلوك القديم، واختبر السلوك الجديد، وشغّل الاختبارات المرتبطة والمتأثرة، وتأكد من عدم حدوث Regression.

النتيجة المقبولة:

- BEFORE: Existing Behavior = PASS
- AFTER: Existing Behavior = PASS
- New Behavior = PASS
- Relevant Regression Tests = PASS

إذا أصبح:

- Existing Behavior = FAIL

فالتنفيذ غير مقبول مهما نجحت الوظيفة الجديدة.

### حماية المنطق المشترك

تكون الحماية أشد عند تعديل منطق مشترك تستخدمه أكثر من وظيفة، مثل:

- Authentication
- Authorization
- Identity
- Financial Posting
- Cash Movement
- Accounting
- Production Tracking
- Customer/Supplier/Employee shared services
- Messaging infrastructure
- Shared DTOs
- Shared repositories
- Shared state
- Common Flutter components
- Central configuration
- أي Service أو Repository أو Engine مشترك

قبل تعديل أي مكوّن مشترك يجب تحديد المستهلكين المتأثرين بالقدر الممكن ضمن النطاق المثبت.

ولا يجوز إصلاح مستهلك واحد بتغيير السلوك المشترك بطريقة تكسر بقية المستهلكين.

### ترتيب الأولويات في الإصلاح

1. الحفاظ على المنطق السليم دون تعديل إن أمكن.
2. إصلاح First Broken Link الحقيقي.
3. إضافة التوسيع الجديد بجانب السلوك السليم إن كان ذلك أنظف.
4. تعديل المنطق السليم فقط إذا ثبتت ضرورة ذلك.
5. عند ضرورة تعديله، المحافظة على Backward Compatibility بقدر ما يتطلب العقد الصحيح.
6. إثبات عدم حدوث Regression بعد التنفيذ.

### Root cause first

قبل أي إصلاح:

- UNDERSTAND
- PROVE CURRENT BEHAVIOR
- FIND FIRST BROKEN LINK
- IDENTIFY ROOT CAUSE
- PROTECT WORKING LOGIC
- IMPLEMENT MINIMUM SAFE CHANGE
- TEST OLD BEHAVIOR
- TEST NEW BEHAVIOR
- REGRESSION VERIFY
- CLOSE

ولا يجوز:

- GUESS
- CHANGE SHARED LOGIC
- SEE IF IT WORKS

### متى يجب التوقف

إذا اكتشف المنفذ أن تنفيذ المطلوب لا يمكن إنجازه إلا بإحدى الحالات التالية:

- كسر عقد أعمال معتمد.
- تغيير قاعدة أعمال خارج التفويض.
- كسر سلوك قائم مطلوب.
- Schema Change غير مخول.
- Migration غير مخولة.
- خسارة أو تغيير بيانات تاريخية.
- Regression لا يمكن منعه ضمن النطاق الحالي.

فيجب التوقف قبل ذلك التغيير ورفع:

1. First Broken Link
2. Root Cause
3. المنطق السليم المتأثر
4. سبب عدم إمكانية المحافظة عليه بالطريقة الحالية
5. الحل الأدنى
6. الحل الأفضل الموصى به
7. المخاطر
8. الاختبارات المطلوبة
9. القرار المطلوب من المالك

## 10A) PERMANENT TEST CODE PRESERVATION POLICY

### المبدأ

كود الاختبار الذي يثبت نجاح مرحلة أو عقد أو إصلاح يجب الاحتفاظ به نهائيًا كجزء من Test Suite.

ممنوع حذف كود الاختبار بعد نجاح المرحلة لمجرد أن المهمة أُغلقت.

الاختبار يمثل:

1. Evidence of Verification
2. Regression Protection
3. Proof of the closed stage/contract

وعليه:

```text
TEST CODE MUST BE PRESERVED.
```

أي اختبار صحيح أُنشئ لإثبات عقد المرحلة يجب أن يبقى قابلاً لإعادة التشغيل مستقبلًا، ما لم يصبح غير صالح بسبب تغيير عقد رسمي معتمد لاحقًا. وفي هذه الحالة يتم تحديث الاختبار بما يتوافق مع العقد الجديد، وليس حذفه لمجرد تجاوز المرحلة.

## 10B) MANDATORY TEST DATA CLEANUP POLICY

بيانات الاختبار مختلفة تمامًا عن كود الاختبار.

أي Test Data ينشئها الاختبار:

- يجب أن ينظفها الاختبار نفسه فور انتهاء التشغيل.
- وينطبق ذلك إذا:
  - نجح الاختبار.
  - فشل Assertion.
  - حدث Exception.
  - توقف التنفيذ جزئيًا.
  - فشل أحد أجزاء الاختبار بعد إنشاء بعض البيانات.

القاعدة:

```text
THE TEST OWNS ITS DATA
→
THE TEST MUST CLEAN ITS DATA
```

## 10C) OFFICIAL-ID CLEANUP

يجب أن يحتفظ الاختبار بالمعرفات الرسمية للسجلات التي أنشأها بنفسه، وأن يستخدم هذه المعرفات في Cleanup.

ممنوع تنظيف البيانات بواسطة:

- مطابقة أسماء عامة.
- مطابقة نصوص غير فريدة.
- DELETE واسع.
- افتراض التواريخ.
- البحث التخريبي.
- حذف جميع بيانات نوع معين.

التنظيف يستهدف فقط:

```text
RECORDS CREATED BY THE CURRENT TEST
```

باستخدام Official IDs والعلاقات الرسمية.

## 10D) SAFE CLEANUP

يجب تصميم الاختبار بحيث يحاول Cleanup حتى عند الفشل.

استخدم آلية مناسبة لبنية الاختبار الحالية مثل:

- try/finally
- test teardown/cleanup mechanism

وفق الأسلوب الأنسب للمشروع.

المهم هو النتيجة:

```text
لا يعتمد تنظيف بيانات الاختبار على نجاح الاختبار نفسه.
```

## 10E) ZERO TEST ARTIFACTS

قبل إعلان نجاح أي اختبار يكتب بيانات في قاعدة الاختبار:

يجب التحقق من عدم بقاء البيانات المؤقتة التي أنشأها الاختبار.

المعيار:

```text
Test Artifacts Remaining = 0
```

ولا تعتبر المهمة مغلقة إذا ثبت وجود Test Data متبقية من اختبارها الحالي.

---

## 10F) DO NOT DELETE REAL DATA

ممنوع على Cleanup:

- حذف بيانات تشغيلية حقيقية.
- حذف بيانات أنشأها اختبار آخر.
- حذف بيانات تاريخية موجودة مسبقًا.
- تنفيذ تنظيف واسع لمجرد ضمان نتيجة صفرية.

إذا لم يستطع الاختبار إثبات ملكيته لسجل:

```text
DO NOT DELETE IT.
```

تُستخدم فقط المعرفات التي التقطها الاختبار عند إنشاء بياناته.

---

## 10G) NO FIX-ONE-BREAK-ANOTHER POLICY

يُضاف هذا المبدأ رسميًا:

```text
ممنوع إصلاح منطق مع كسر منطق آخر صحيح.
FIXING A MUST NOT BREAK B.
```

كل إصلاح يجب أن يمر بالتسلسل:

1. UNDERSTAND
2. PRESERVE
3. IMPROVE / MINIMUM SAFE FIX
4. TARGETED TEST
5. REGRESSION TEST
6. VERIFY PRESERVED CONTRACTS
7. CLEAN TEST DATA
8. FINAL VERIFICATION

نجاح الوظيفة الجديدة وحده لا يكفي لإغلاق المهمة.

## 10H) REGRESSION RESPONSIBILITY

عند تعديل منطق قائم:

- يجب تحديد العقود والوظائف المجاورة التي يمكن أن يتأثر سلوكها بالتعديل.
- ثم إجراء Regression Verification عليها.
- ويجب إثبات أمرين قبل الإغلاق:

```text
A) TARGET BEHAVIOR VERIFIED
B) PREVIOUS VALID BEHAVIOR PRESERVED
```

إذا نجح A وفشل B:

```text
المهمة ليست ناجحة.
```

---

## 10I) WHEN REGRESSION IS FOUND

إذا كشف الاختبار أن الإصلاح الجديد جرح منطقًا آخر:

ممنوع الاستمرار بإصلاحات عشوائية متتابعة.

ابدأ بـ:

1. First Failed Contract
2. First Broken Link
3. Root Cause

ثم حدّد:

- Minimum Safe Fix

إذا كان الإصلاح داخل نطاق التفويض، نفّذ أقل إصلاح آمن ثم أعد:

- Targeted Tests
- Regression Tests

أما إذا كان يتطلب:

- تغيير قاعدة أعمال.
- تغيير عقد معتمد.
- Schema Change غير مصرح.
- تغيير منطق مغلق سابقًا.

فتوقف واطلب موافقة المالك.

---

## 10J) TESTS ARE CLOSURE EVIDENCE

الاختبارات الناجحة التي تثبت عقدًا أو مرحلة مغلقة تعتبر حماية دائمة ضد Regression.

لذلك:

- لا تحذف Test Code الصحيح بعد الإغلاق.
- احتفظ به ضمن مجموعة الاختبارات الرسمية للمشروع.

لكن:

- احذف Test Data التي ينشئها كل تشغيل.

القاعدة المختصرة:

```text
KEEP THE TEST.
CLEAN ITS DATA.
PRESERVE EXISTING LOGIC.
PROVE NO REGRESSION.
```

## 11) الحكم النهائي

هذا المستند هو المرجع الرسمي لسياسة قواعد البيانات وإنفاذ سلامة المنطق في مشروع LUMAR ERP، ويُستشهد به في أي توثيق أو مراجعة أو تقييم أو إغلاق مهمة أو إصلاح أو اختبار أو Migration.

ولا يُسمح بتجاهل هذه السياسة أو تجاوزها، إلا إذا صدرت تعليمات جديدة ومكتوبة وموقعة من مالك المشروع ياسين.
