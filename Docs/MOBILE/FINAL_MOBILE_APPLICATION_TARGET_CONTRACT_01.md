## [REALITY CHECK - حقائق الوضع الحالي]

يجب أن ينص هذا القسم صراحة على الحقائق التالية دون أي افتراضات:

1. لم يتم إثبات وجود تطبيق Android تشغيلي داخل الكود الحالي.
2. لم يتم إثبات وجود:
   - Flutter Mobile Application جاهزة.
   - Android Project جاهز.
   - شاشات Mobile جاهزة.
   - Mobile Navigation جاهز.
   - Mobile State Management جاهز.
   - Mobile Services جاهزة.
   - Mobile Repositories جاهزة.
   - Mobile Controllers جاهزة.
   - Mobile APIs مخصصة للتطبيق ومكتملة.
3. نتائج التدقيق السابقة أثبتت وجود:
   - جداول.
   - علاقات.
   - بيانات تشغيلية.
   - آثار استخدام حقيقية.
   - عقود وظيفية.
   داخل قواعد البيانات. لكنها لم تثبت وجود التطبيق نفسه داخل الكود الحالي.
4. عند استخدام عبارة "جاهز لإعادة البناء" يجب أن يكون المقصود حصراً:
   - تم استعادة قدر كافٍ من المعرفة والبيانات والعقود التشغيلية لإعادة بناء التطبيق.
   - ولا يجوز تفسير العبارة على أنها: التطبيق موجود حالياً، أو قابل للتشغيل، أو موجود في المستودع، أو يحتاج فقط إلى تشغيل أو ربط.
5. يجب أن يحتوي هذا العقد النص التالي حرفياً:

   Database Knowledge Exists.
   Android Application Does Not Exist.
   Android Application Must Be Rebuilt From Scratch.

6. قاعدة LUMAR_ERP لا تُستخدم لإثبات وجود التطبيق الحالي. بل تُستخدم فقط لاكتشاف:
   - الوظائف السابقة.
   - الشاشات السابقة.
   - مصادر البيانات السابقة.
   - العقود والسيناريوهات التشغيلية السابقة.
7. قاعدة LUMAR_ERP_ES_VALIDATION هي قاعدة التطوير الرسمية الحالية. لكن وجود الجداول أو البيانات داخلها لا يعني تلقائياً وجود تطبيق Android أو Flutter أو Mobile APIs جاهزة.
8. العقد النهائي يجب أن يفرق بوضوح بين:
   - ما تم إثبات وجوده في قاعدة البيانات.
   - ما تم إثبات وجوده في الكود.
   - ما يجب إعادة بنائه من الصفر.
9. أي عنصر لم يتم إثبات وجوده في الكود الحالي يجب تصنيفه على أنه REBUILD REQUIRED وليس EXISTS أو READY TO RUN.
10. الاستنتاج الرسمي للمشروع في هذه المرحلة هو:
    - تم استعادة المعرفة التشغيلية للتطبيق بدرجة كبيرة.
    - أما التطبيق نفسه فيجب إعادة بنائه من الصفر فوق البيئة الحالية للمشروع وقاعدة LUMAR_ERP_ES_VALIDATION.

## [DATABASE ROLES - أدوار قواعد البيانات]

### أولاً: LUMAR_ERP (القاعدة التاريخية)

**دورها الوحيد في هذا العقد:**
- استعادة تصور التطبيق السابق.
- معرفة الوظائف التي كانت موجودة أو مخططة.
- معرفة الشاشات المحتملة.
- معرفة مصادر البيانات التاريخية.
- معرفة العلاقات التشغيلية التي كان التطبيق يعتمد عليها.

**LUMAR_ERP ليست:**
- قاعدة التطوير الحالية.
- مصدر الحالة الحالية للمشروع.
- قاعدة التنفيذ.
- قاعدة الاختبار.
- مرجعاً لاختيار الأعمدة أو العلاقات الحالية.
- مرجعاً لإنشاء Migration جديدة.
- مرجعاً يسمح بإرجاع النظام إلى تصميم أقدم.

**قاعدة LUMAR_ERP متاحة للقراءة فقط.**

**ممنوع نهائياً:**
- تعديلها.
- تنفيذ Migration عليها.
- إضافة جدول أو عمود أو فهرس إليها.
- حذف أو تحديث أي سجل فيها.
- تشغيل التطبيق الجديد عليها.
- استخدام بيانات دخول تاريخية منها.
- اعتبار مخططها مطابقاً لمخطط التطوير الحالي.

### ثانياً: LUMAR_ERP_ES_VALIDATION (قاعدة التطوير الرسمية)

**هي قاعدة التطوير الحالية والرسمية.**

**هي القاعدة الوحيدة التي سيُبنى ويُختبر عليها تطبيق Android الجديد مستقبلاً.**

**جميع عمليات التنفيذ المستقبلية يجب أن تعتمد على الحالة الفعلية الحالية داخل LUMAR_ERP_ES_VALIDATION وتشمل:**
- عقود Backend.
- APIs.
- Queries.
- عمليات الكتابة.
- المصادقة.
- الجلسات.
- الصلاحيات.
- اختبارات التكامل.
- Ownership.
- الاختبار اليدوي.
- اختبارات Android.

**إذا احتوت LUMAR_ERP_ES_VALIDATION على وظائف أحدث من القاعدة التاريخية، تكون الأولوية دائماً للوظائف الأحدث.**

**لا يجوز حذف وظيفة حديثة أو إرجاع تصميم حالي إلى تصميم أقدم لأن القاعدة التاريخية لا تحتوي عليه.**

## [PRIVACY AND OWNERSHIP CONTRACT - عقد الخصوصية والملكية]

1. يمنع العميل من قراءة بيانات عميل آخر.
2. يمنع الموظف من قراءة بيانات موظف آخر.
3. يمنع الاعتماد على CustomerId أو EmployeeId القادم من Flutter لتطبيق الملكية.
4. تطبق الملكية داخل Backend.
5. يمنع إرسال PasswordHash.
